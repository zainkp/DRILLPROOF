# 05 — Demo Story, Pitch Support, and Definition of Done

## Demo institution
Use a fictional institution such as **Northstar Campus** with:
- Academic Block
- Administration Block
- Student Residence

Use fictional staff names and contact details. Make all demo data visibly illustrative.

## Suggested demo scenario
A judge should see one complete preparedness-improvement loop, not a tour of disconnected pages.

### Scene 1 — Public emergency access
1. Open the landing page.
2. Click `View Demo Building` or scan/show the QR code.
3. Open the Academic Block emergency page.
4. Show the assembly point, emergency contacts, floor information, and hazard-specific instructions.
5. Explain that the QR code provides quick access to the institution's approved information; it is not a live emergency detection system.

### Scene 2 — Admin readiness overview
1. Sign in through demo access.
2. Open the dashboard.
3. Point out inspections due, completed drills, and open corrective actions.
4. Show that the information is organized by building and operational task.

### Scene 3 — Drill workflow
1. Create or open an earthquake or fire drill.
2. Start the timer.
3. Record floor/team check-ins manually using demo controls.
4. Complete the drill and enter one observation.
5. Show the drill summary.

### Scene 4 — Corrective action
1. Convert the observation into an action: “West stairwell exit obstructed during drill.”
2. Assign it to Facilities and set a due date.
3. Change status to resolved and add a resolution note.
4. Return to dashboard/report and show the open action count or status has changed.

### Scene 5 — Broader product story
Explain that the same structure supports other hazard templates and multiple institution types, including offices and workplaces. The demo implements a focused sample workflow; it does not claim that every future integration is already built.

## What to say honestly
- “This prototype demonstrates the workflow using sample data.”
- “Check-ins are manually recorded in this version.”
- “The QR page displays the building's configured emergency information.”
- “We are not detecting hazards or automatically tracking people.”
- “A real deployment would require institution onboarding, verified emergency plans, security controls, and validation by qualified safety professionals.”

## Definition of done
The prototype is ready when:
- [ ] Landing page communicates the product clearly.
- [ ] Logo and red/neutral visual identity are consistent.
- [ ] Public emergency page works without admin login.
- [ ] Admin/demo login leads to the dashboard.
- [ ] Building data and QR destination are coherent.
- [ ] At least one inspection can be submitted.
- [ ] At least one drill can be started and completed.
- [ ] Drill progress/check-ins can be recorded manually.
- [ ] An observation can create a corrective action.
- [ ] A corrective action can be assigned and resolved.
- [ ] Dashboard metrics update from the same underlying demo data.
- [ ] No visible button is knowingly inert.
- [ ] Mobile emergency page and desktop dashboard are usable.
- [ ] All simulated or illustrative data is labelled honestly.

## Suggested final pitch framing
“Most institutions already have emergency plans. The challenge is making sure people can execute them—and ensuring every drill or inspection leads to measurable improvement. DRILLPROOF connects building emergency information, safety inspections, mock drills, and corrective actions in one operational readiness platform.”

Avoid saying:
- “No one else does this.”
- “We guarantee safety.”
- “We automatically detect every emergency.”
- “We replace emergency services.”
- “We certify legal compliance.”
